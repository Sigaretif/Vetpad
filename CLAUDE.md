# Vetpad — Project Rules

Astro 7 SSR app (React 19 islands, Tailwind 4, Supabase auth) deployed to Cloudflare Workers. Product context: `@context/foundation/prd.md`, `@context/foundation/tech-stack.md`. Setup, env vars and deploy: `@README.md`. Scripts: `@package.json`. CI gate: `@.github/workflows/ci.yml`.

## Hard rules

### The project runs with zero configuration — keep it that way

- The app must start, build, lint and typecheck on a fresh clone with **no `.env`, no `.dev.vars`, no Supabase, no API keys**. Verified in that exact state: `npm run dev`, `npm run build`, `npm run lint`, `npx astro check` and `npm test` all pass, `/` and `/auth/signin` return 200, `/dashboard` redirects to `/auth/signin`, and `src/layouts/Layout.astro` renders the warning banner from `missingConfigs`. Only `npm run smoke` and `npm run test:db` need a live local Supabase.
- **Never refuse to run, build, or implement a task because a secret or an external service is absent.** Missing configuration is a supported, first-class state of this app — not a blocker, and never a reason to stop and ask the user to set something up. Build the feature, let its integration degrade, and surface the gap in the banner.
- Every new integration repeats the existing pattern, in all four places: an `envField(...)` with `optional: true` in `@astro.config.mjs`; a factory that returns `null` when its secrets are missing (`src/lib/supabase.ts`, `src/lib/audit/provider.ts`); a null-check at every call site (`src/middleware.ts`, `src/pages/api/auth/signin.ts`, `src/pages/api/audits.ts`); and a `ConfigStatus` entry in `src/lib/config-status.ts` so the absence shows up in the banner instead of as a crash.
- Never make an env field required, never `throw` at module load over a missing secret, and never let a route return 500 because an integration is unconfigured. Degrade the feature, keep the page rendering.

### Secrets and data access

- `createClient()` from `@/lib/supabase` returns `null` when `SUPABASE_URL`/`SUPABASE_KEY` are unset. Null-check it before every use — see `src/middleware.ts` and `src/pages/api/auth/signin.ts`.
- Read those secrets only from `astro:env/server`. They are declared `access: "secret"` in `@astro.config.mjs` — never `process.env`, never client-side.
- `SUPABASE_KEY` is the **publishable** key (`sb_publishable_…`, the key Supabase used to call `anon`), and requests carry the user's cookie session (`@supabase/ssr` in `src/lib/supabase.ts`). Once tables exist, **row-level security is the only thing protecting data** — there is no authorisation layer in application code to fall back on. Treat a missing or permissive policy as a security bug, not a TODO.
- Never introduce a `service_role` / `secret` key (`sb_secret_…`), and never reach for one to work around a policy that rejects a query: it bypasses RLS entirely. Fix the policy instead.
- Every new table gets `alter table … enable row level security` plus one policy per operation (select/insert/update/delete) and role — no `for all`, no `using (true)`. This lands in the first migration that creates the table, not in a later hardening pass. A table written only by a `security definer` trigger has no insert/update/delete policies at all — that denial is intended, not a gap to fill; `supabase/migrations/20260926185936_create_members.sql` is the reference.
- The hosted Supabase project runs with **Data API on, automatic exposure of new tables on, and automatic RLS on**. Two things follow. A migration needs no `grant`: Supabase already grants `select/insert/update/delete` on every new `public` table to `anon` and `authenticated`. And because that grant is automatic, **the RLS policy is the single gate, not the second of two** — a table whose policies are missing or permissive is reachable by anyone holding the publishable key, including an unauthenticated visitor. Write the policies in the creating migration and treat a gap as a live exposure, not a TODO.
- Know the two denial signatures, because the tempting fix for both is the one thing that is never the fix. RLS on with no `select` policy returns an **empty array and HTTP 200** — it looks like missing data, not like a permission error. A blocked write fails with `new row violates row-level security policy`. Neither is repaired with a `secret` / `service_role` key; both are repaired in the policy.
- Scope those policies the way the PRD's requirements do. A note: `insert` sets the author from `auth.uid()` and never reassigns it, `update` and `delete` check it (FR-012, FR-015), `select` is open to every authenticated member (FR-013). Offers, searches and criteria: full CRUD for any member (Access Control, Roles) — and deleting an offer takes every member's notes with it, a cascade the PRD weighed and accepted (FR-015). Criteria are split as FR-002 splits them: any member edits the team's shared limits, while a member's additional requirements are written, edited and deleted only by their author, and read by everyone. "Flat roles, no restricted destructive actions" is the coarse summary of the same thing: the restriction is authorship, never a role tier.
- `@context/foundation/prd.md` binds this file. Where the PRD leaves something open, point at its open question instead of inventing an answer here; where it looks self-contradictory, fix the PRD rather than writing the resolution into a rule. `@context/foundation/shape-notes.md` is the longer record behind it — useful for _why_ a requirement reads as it does, never a source that overrides it.
- The model-provider key for the AI audit (`@context/foundation/prd.md`, FR-010) is `ANTHROPIC_API_KEY`. It follows the zero-config pattern above and is **server-only**. Never call a model provider from a React island — islands ship to the browser and the key would land in the client bundle. `src/lib/audit/provider.ts` is the one module that hands the key to anything and the one module that talks to the provider; `src/lib/config-status.ts` only asks whether the key is set, for the banner and for `isAuditAvailable()` — which is how a view learns whether an audit can be started, never by importing the provider module, which would load the SDK with a page render. A secret has six places to land, and a second provider key or a renamed one repeats all of them: `astro.config.mjs` schema, `.env`, `.dev.vars`, `.env.example`, plus the Cloudflare secrets and the GitHub repository secrets that `@.github/workflows/ci.yml` injects into the build — into the `ci` job's build step only; the `smoke` job gets no provider key, on purpose.
- Only the listing's text and the team's criteria may be sent to the model provider. **Members' notes never leave the system** (`@context/foundation/prd.md`, Non-Functional Requirements): they are conclusions drawn from the audit, never an input to it (Business Logic). Feeding notes into the audit prompt looks like a quality improvement and is a privacy breach. Row-level security cannot hold this rule — every member reads every note — so the code's structure does: `auditNoNotesConfig` in `@eslint.config.js` makes an import of the notes module an error under `src/lib/audit/` and in `src/pages/api/audits.ts`, and the audit's input is built from a whitelist of `public.offers` columns, never from `raw` — `AUDIT_OFFER_COLUMNS` in `src/lib/audit/input.ts` is the reference, and a column the audit should read is added to that list, never read around it.
- **The advertiser's phone number and name never reach the database.** Both ingestion paths hand them to you: `ad.contactDetails.phones` / `ad.owner.contacts` when fetching otodom directly (`@context/foundation/ingestion/otodom_fetching.md`, section 1), and `sellerPhone` / `agencyName` through the extraction-service fallback — where `agencyName` holds a private seller's own name (`@context/foundation/ingestion/otodom_apify.md`, section 6.1). Drop them at the fetch boundary: no column stores them, no audit prompt receives them, and nothing in the product needs them. FR-004 saves the listing, not the seller. The rule covers the structured fields and the `raw` column: `raw` is built from a whitelist of `ad` keys, never by deleting known fields, and `target` is narrowed to `OfferType`/`ProperType` because it repeats the seller's account id (`src/lib/otodom/map.ts` is the reference). What happens to a contact the advertiser typed into the listing's own text is decided in `@context/foundation/prd.md`, Non-Functional Requirements — follow it there.

### Cloudflare Workers runtime

- **Deploying, debugging production, or hitting something that looks like a platform bug: read `@context/foundation/deployment-runbook.md` first.** It records what the platform actually did during the first deploy, including a table of symptoms that name the wrong cause — `1102` reads like an application bug and is a plan limit, a silent Workers Builds is a branch-name default, a paused Supabase project breaks login without raising the config banner. It also holds the rollback, log and contingency procedures, and the trigger conditions for the Apify fallback and for buying Workers Paid.
- The deploy target is Cloudflare **Workers**, not Pages: `@wrangler.jsonc` sets `main` to the `@astrojs/cloudflare` server entrypoint and `@README.md` deploys with `npx wrangler deploy`. Never run `wrangler pages deploy`.
- The audit's ~3-minute budget (`@context/foundation/prd.md`, Non-Functional Requirements) fits in one HTTP request: the binding limit is **CPU time**, which waiting on `fetch` does not consume. The concrete ban is the next bullet; any other CPU-bound pass over a full page body gets its per-request CPU number checked in the Workers dashboard before it merges. Current per-plan numbers: <https://developers.cloudflare.com/workers/platform/limits/>.
- Do not parse a whole otodom.pl page inside the Worker: no HTML-parsing dependency (`cheerio`, `node-html-parser`, `linkedom`) enters `@package.json`, and no `src/pages/api/` handler builds a document or walks a DOM over the fetched page. For a single pasted listing (FR-004) the path is section 7.1 of `@context/foundation/ingestion/otodom_fetching.md`: fetch the offer page, pull `__NEXT_DATA__` out with one bounded `RegExp`, parse the JSON — no `buildId`, no pagination, no state. Section 1 of the same file lists the paths `robots.txt` puts off-limits, the GraphQL endpoint among them, and section 9.1 records what this platform does and does not let a scraper do. If ingestion ever stops working — `__NEXT_DATA__` gone, or otodom returning 403 to Cloudflare's egress IPs — the fallback is still not a parser inside the Worker: it is a third-party extraction service the Worker calls with one `fetch`, replacing the otodom scraper rather than sitting beside it. `@context/foundation/ingestion/otodom_apify.md` is the verified path for that, request shape and failure modes included; adopting it is a decision to raise with the user.
- Never use a module-scope variable as a cache, a queue, a lock or a job registry — that state belongs in Postgres.
- Before importing any `node:*` module, verify it is supported under `nodejs_compat` for the `compatibility_date` in `@wrangler.jsonc`. `node:child_process`, `node:worker_threads`, `node:vm` and `node:http2` are non-functional stubs, and they fail on a deployed request — not at `npm run build` or `npx astro check`.
- `.dev.vars` is the workerd half of the local setup (`@README.md`); missing it is the zero-config state above, not a gap to fill. `npm run build` copies it into `dist/server/`, and `npm run preview` reads the copy: a value changed in `.dev.vars` reaches the preview only after a rebuild, and restarting the preview is not enough.

### Framework

- `output: "server"` is global. Do not add `prerender` exports; no route in `src/` uses one.
- Never write `"use client"` / `"use server"`. This is Astro, not Next.js; the directives do nothing and signal the wrong mental model for the file.
- A page that has to answer 404 sets `Astro.response.status = 404` and renders its not-found branch; a top-level `return` in `.astro` frontmatter crashes the `@typescript-eslint/no-misused-promises` rule in `npm run lint`. `src/pages/offers/[id].astro` is the reference.

### Git

- Never rewrite history (`--force`, `--amend`, `reset --hard`, `git branch -D`), and never commit or push by hand — commits and pushes go through a skill, never through a raw `git commit` or `git push`.
- `/10x-implement` is the skill that commits during implementation: its phase-end commit ritual and its epilogue commit land on the branch you are standing on — normally local `master` — and stay local. It never pushes. Local `master` ahead of `origin/master` by those commits is an expected state, not a mess to clean up by hand.
- Two skills push, and **the agent asks which one before it starts, every time** — it never picks for the user. Both take the local commits ahead of `origin/master` (typically `/10x-implement`'s) together with anything still uncommitted; either part may be empty. `/git-ship` is the reviewed path: a `10x-` branch, a push, a pull request, and the user back on `master` — level with `origin/master` — with a clean tree. `/git-land` is the unreviewed one: it commits what is uncommitted on `master` and pushes `master` straight to `origin`, local commits included, no branch and no PR, and it aborts unless the user is already standing on `master`. Neither is the default, because the choice is the user's; when the answer is "whichever", that means `/git-ship`, since a PR can be closed and a push to `master` cannot be taken back. The rest of the workflow is in `## Git workflow` below.

## Product invariants

These come from `@context/foundation/prd.md` (Success Criteria → Guardrails, Non-Functional Requirements). Each one looks like a reasonable default to break, and breaking any of them silently is a product failure, not a style slip.

- An attribute the listing does not state is never reported as "no", as `0`, or as any empty-looking falsy value — a fabricated fact could cost the team a flat. The presentation is settled in `@context/foundation/prd.md` (Open Questions, resolved block); `src/components/offers/Unstated.astro` is the reference.
- **The source hands you that falsy value already made.** Verified on a live offer 2026-09-20: otodom returns `characteristics.rent` as the string `"0"`, not as an absent key. Mapped straight through, the card reads "Czynsz: 0 zł" — an invented fact about a building where it is almost never true, and the guardrail above is broken by code that looks correct. It also omits the key entirely, and sends `"1"` on a rental. Every numeric characteristic goes through one function — key absent, empty, unparseable or `≤ 0` is unknown — `numericOrUnknown` in `src/lib/otodom/map.ts`. The traps are documented at `@context/foundation/ingestion/otodom_fetching.md` § 7.1.
- **Only a sale of a flat is saved** (`@context/foundation/prd.md`, FR-005). A rental or another property type is refused after the fetch with nothing stored. The discriminator is `ad.adCategory`, never `ad.category` — the latter's `name` is an empty array, so a gate built on it passes everything (`@context/foundation/ingestion/otodom_fetching.md` § 7.4).
- **Human-authored notes are never overwritten by machine action.** A re-fetch (FR-009) replaces scraped listing data only; after it, every note reads exactly as its author left it.
- Every _positive_ audit finding — a red flag, a cost, a mandatory condition — carries a **verbatim excerpt** of the listing text it rests on. A finding that cannot be grounded in the text is not reported at all. Missing-data findings carry no excerpt, because an absence cannot be quoted. Two limits keep this extraction rather than inference (FR-011): a cost is reported only where the listing names it — "likely" costs were cut for exactly this reason — and missing-information findings cover only the decision-critical attributes FR-011 lists and what the members' additional requirements ask about, not an inventory of everything the text omits; `DECISION_CRITICAL` in `src/lib/audit/input.ts` is that list in code, and it changes only after FR-011 does. The model is asked for all of this and trusted with none of it: `groundFindings` in `src/lib/audit/grounding.ts` is the one gate between its answer and what is stored, and it only takes away — it never repairs an excerpt, never adds a finding, and never concludes from an empty column that the listing is silent. An excerpt is checked against the stored `title` and `description`, never against `raw`.
- A failed fetch is reported explicitly as a fetch problem. **Never create or save a blank, partial or silently empty offer.**
- No machine action re-runs or removes an audit. When the listing or the criteria change, the existing audit is flagged **stale** and the member is prompted to re-run it. Removal is always a deliberate member action; nothing expires on its own. What is not a reason to flag an audit stale, and what a re-run that fails leaves behind, are settled in `@context/foundation/prd.md` (FR-010, FR-009) — follow them there.
- Every fetch, re-fetch and audit is a **deliberate manual action** (Non-Goals). No scheduled jobs, no background re-scraping, no notifications.
- **Archiving takes an offer off the board and changes nothing else** (`@context/foundation/prd.md`, FR-014). Every note and the stored audit read exactly as before, in the archive and after a restore, and notes and a re-fetch keep working on an archived offer. An audit of an archived offer cannot be started until the offer is restored: `src/components/offers/OfferAudit.astro` renders no `AuditRunner` for it, and `src/pages/api/audits.ts` refuses with `offer_archived` before it claims the row or looks for a provider key. **Nothing restores an offer as a side effect** — not a pasted address of it (FR-005), which opens the card and offers the restore, not a re-fetch, not the deletion of an account — and an offer never leaves the board silently: wherever an archived offer is shown, so is who archived it and when.
- Audit correctness outranks audit speed and audit cost (`@context/foundation/prd.md`, Non-Functional Requirements). The audit's default model is `claude-opus-5-5` at reasoning effort `medium`, called through the official Anthropic SDK, `@anthropic-ai/sdk` (the user's choices, 2026-10-06). Neither the model nor the effort is hard-coded at the call site: `src/lib/audit/settings.ts` holds the defaults (`DEFAULT_AUDIT_SETTINGS`) and the closed lists a team may choose from, the team's choice is the one row of `public.audit_settings`, which members change on `/criteria` (FR-010), and the audit route takes both values from `loadAuditSettings` — a failed read refuses the audit and never falls back to the default. Changing the default, widening the lists (they stand in that module and in the table's checks, so a new option is a migration) or moving `AUDIT_MAX_TOKENS` in the same module is a decision about latency and spend to raise with the user, never something an implementation picks.

## Structure

Layout and route protection are in `@README.md`. The part it does not state: `src/middleware.ts` resolves the user into `context.locals.user`, typed in `src/env.d.ts`. shadcn's style, aliases and icon library: `@components.json`. Config: `@astro.config.mjs`, `@wrangler.jsonc`, `supabase/config.toml`.

- `src/lib/otodom/` is the ingestion module: URL normalisation, the page fetch, and the mapper that holds the flat-sale gate, the unknown-not-zero rule and the personal-data whitelist. `src/pages/api/offers.ts` is the reference domain form route (one distinguishable `?error=` message per failure reason), and `src/pages/offers/[id].astro` is the offer card page, protected through `PROTECTED_ROUTES` in `src/middleware.ts`.
- `src/lib/map-link.ts` is the reference for the link to a map (FR-008): it is built from the location label and the street, never from the coordinates, an offer with no label gets no link, and what the row holds lands only in the value of the `query` parameter. A view takes the address from it and never assembles one itself — `src/components/offers/OfferCard.astro` is the reference — and the next link built from stored text follows it rather than building a second mechanism. `tests/lib/map-link.test.ts` is the reference test.
- `src/middleware.ts` is the place that never turns a Supabase Auth outage into a sign-in redirect, and the reference for a log entry from outside a route. `src/lib/auth-error.ts` is the reference for classifying an Auth error — the middleware and `src/pages/api/auth/signin.ts` share it rather than each keeping a condition of its own, and an error it cannot recognise is an outage, never a signed-out member. A route behind the middleware does not ask whether its `user: null` came from an outage. `tests/middleware.test.ts` is the reference test.
- `src/pages/dashboard.astro` is the shared offer board (FR-006). `src/lib/offer-board.ts` is the reference for its sort (`?sort=&dir=`, unknown values last via `nullsFirst: false`) and holds `auditStatus()`, whose rule is that only a stored result is an audit: an offer whose attempt is running or failed is still not audited, and a failed read of the audits is `unknown`, never "not audited". A stored result reads as `audited` only when it is known to be up to date: one the listing or the criteria have moved past is `stale`, and one whose freshness could not be established — a failed read of it included — is `freshness_unknown`, never `audited`. `loadAuditIndex` in `src/lib/audit/store.ts` is its data source, `loadBoardFreshness` in `src/lib/audit/freshness.ts` is the read behind those two statuses, and `src/components/offers/AuditStatusBadge.astro` is the one place that status gets a label, and its value as `data-audit-status`. The board's container carries `data-board-state="ok"|"error"`, which `scripts/smoke.mjs` checks, because a failed read renders with 200 just like an empty board; `data-limits-state` beside it does the same for the team's limits, whose failed read is never shown as "no breaches", `data-audits-state` for the audits, and `data-audit-freshness-state` for their freshness.
- `supabase/migrations/20260927144141_create_team_criteria.sql` is the reference for a singleton the team shares: the migration inserts the one row, members get `select` and `update` policies and no `insert`/`delete` (clearing the limits is an update that writes nulls), and the criteria revision counter has no write policy at all — only a `security definer` trigger bumps it, and only on a real change. `src/lib/criteria.ts` is the reference for reading the criteria (a failed read is its own state, never "no limits", and so is a value in the row that does not read as a limit — zero, a negative number, non-numeric text, an empty city — which is never "no limit", while a number PostgREST sends as text reads as that number; members' requirements are read most recently edited first; `tests/lib/criteria.test.ts` is the reference; `/criteria` carries the state as `data-criteria-state`) and `src/lib/team-limits.ts` for comparing an offer with the limits (only a stated fact breaks one). Breaches always come back in the order `city`, `price_above`, `price_below`, `area_below`. For limits the form and the table's checks do not allow, the function judges each price bound on its own — an inverted range can yield both price marks — reads an empty city limit as no limit, and compares a city limit containing a comma as a whole, so it marks every offer with a stated location; `tests/lib/team-limits.test.ts` is the reference. The audit reads the criteria through `loadAuditCriteria` in `src/lib/criteria.ts` and through nothing else: the limits, the requirements' texts without their authors — oldest first, so the same criteria always number the same way — and the revision, read before the criteria and again after them, so that a change in between repeats the read and a second one fails it. `criteria_revision.revision` is stored with the audit, and `auditFreshness` in `src/lib/audit/freshness.ts` compares it with the current one — which a view reads through `loadCriteriaRevision` in `src/lib/criteria.ts` — to flag the audit stale; the next reader of the revision goes through them rather than building a second mechanism.
- `public.members` (`supabase/migrations/20260926185936_create_members.sql`) and `src/lib/members.ts` are the reference for naming a member — a note's author, the member who ran an audit, the one who last changed the audit settings and the one who archived an offer are named through them, and the next name follows them rather than building a second mechanism. The name is the email address. A `null` author column is a deleted account, rendered „osoba z usuniętym kontem” — with or without a client, because it is a fact from the row that needs no read. A failed read, a missing `members` row or a `null` email is the `unknown` variant: it names nobody and is never shown as a deleted account. `tests/lib/members.test.ts` is the reference for both. `scripts/smoke.mjs` checks the table's RLS from both sides, since a blocked read answers 200 with `[]`.
- `supabase/migrations/20260926202537_create_offer_notes.sql` is the reference for a table restricted by authorship: `select` open to every signed-in member, `insert`/`update`/`delete` policies on `author_id = auth.uid()`, and a freeze trigger that keeps what a row is about and who wrote it on update, letting `author_id` go `null` only through `on delete set null` once the account is gone; `supabase/migrations/20260927133501_offer_notes_server_timestamps.sql` adds the insert half, so the row's dates are always the database's. `src/lib/notes.ts` is the reference for reading an offer's notes (a failed read is its own state, never "no notes"), and `resolveAuthors` in `src/lib/members.ts` for naming many authors with one query — S-11 reuses them rather than building a second mechanism. `src/components/offers/OfferView.astro` puts the offer card beside the team column, which holds the audit (`src/components/offers/OfferAudit.astro`) above the notes (`src/components/offers/OfferNotes.astro`) — two reads of their own, so each renders whatever the other's read did.
- `src/lib/audit/` is the audit module (FR-010, FR-011), one concern per file: `src/lib/audit/input.ts` (the whitelist of offer columns, the decision-critical attributes, the listing fingerprint), `src/lib/audit/prompt.ts` (the instruction and the message), `src/lib/audit/schema.ts` (the answer's JSON Schema and the readers of an answer and of a stored result), `src/lib/audit/grounding.ts` (the gate between the answer and what is stored), `src/lib/audit/failure.ts` (every reason an audit ends without a result, the one sentence a member reads for each, and the time limits), `src/lib/audit/provider.ts` (the model call), `src/lib/audit/store.ts` (every write and read of `public.offer_audits`), `src/lib/audit/settings.ts` (the team's model and effort) and `src/lib/audit/stream.ts` (the browser's reading of the route's answer, as pure functions). The instruction was approved by the user word for word on 2026-10-07 and holds more than the plan of S-04 listed, by their decision; what it counts as a finding is recorded in `@context/foundation/prd.md` (Open Questions, resolved block). Change it deliberately, never in passing, and never by putting a listing's wording into it, which a model could hand back as an excerpt. The failure, settings and stream modules are imported by islands, so `@/lib/supabase` — and `astro:env/server` behind it — enters them only through `import type`; the provider module is server-only, and nothing a page render loads imports it.
- `supabase/migrations/20261007073300_create_offer_audits.sql` is the reference for state that triggers own and for a row that is its own lock: one row per offer holds the latest attempt and the last result that succeeded, the triggers — never the client — set the dates and the people and allow the moves between states, an attempt on an offer whose attempt is still running is refused with the project's own SQLSTATE `VP001`, and there is no delete policy, because an audit goes only with its offer. The update function was replaced once, by `supabase/migrations/20261009191000_offer_audits_ended_by_starter.sql`, which is the one to read and to copy from: only the member who started an attempt ends it, since the result is signed with that member's name. It is also the reference for more than one `on delete set null` column in a row: each has its own deleted-account branch in the trigger, checked before any other rule. How long an attempt may run before another may take the row over stands in that migration and as `AUDIT_STALE_ATTEMPT_MS` in `src/lib/audit/failure.ts`: change the two together, and keep the order that module states — the provider's deadline, then that threshold, then the browser's limit. `supabase/migrations/20261007073258_create_audit_settings.sql` repeats the singleton of the team's limits; the settings are not criteria, so nothing in it touches `criteria_revision`. `src/pages/api/audits.ts` is the reference for the order of a paid action — everything that can be checked for free, then the claim of the row, then the provider, with no retry of a paid call — and for ending the attempt in the database on every way out after the claim; `src/lib/audit/store.ts` is the reference for writes judged by the error's code and by the number of rows they reached. The SDK's client is built per request (`createAuditProvider` in `src/lib/audit/provider.ts`), never at module scope.
- `loadOfferAudit` and `loadAuditIndex` in `src/lib/audit/store.ts` are what the views read, and a failed read is never "not audited": the card then renders no audit button, because a run started from it could pay for an audit the offer already has. On the audit section, `src/components/offers/OfferAudit.astro`, `data-audit-state` and `data-audit-available` never stand in for each other: the first says what the audit's data is — `auditDataState()` in `src/lib/audit/store.ts` is the one mapping, in which the latest attempt speaks before the stored result — and the second says whether the application holds a provider key. `/criteria` carries the settings' read as `data-audit-settings-state`. Everything a finding carries is rendered as text, because any member can write `public.offer_audits` through the Data API: a label, a question or an excerpt never goes through `set:html`, into an attribute or into an island (`tests/components/offers/render.test.ts` is the reference). An audit also stores `criteria_revision` and `listing_fingerprint` (`listingFingerprint` in `src/lib/audit/input.ts`), which no view shows — they are what `src/lib/audit/freshness.ts` compares. The fingerprint carries its version, and a change to `AUDIT_OFFER_COLUMNS` or to their order needs a new one.
- `src/lib/audit/freshness.ts` is the one place a stored audit is compared with what stands now (FR-003, FR-009): `auditFreshness` takes the criteria revision and the listing fingerprint the audit recorded and the current ones, and the card and the board ask it rather than comparing on their own. A side that cannot be compared — a failed read of the revision, an offer row that does not read, a fingerprint of another version — is never read as "nothing changed": the other side may still prove the audit stale, and when it does not, the answer is `unknown`, never `fresh`. Nothing is stored and nothing is written to `public.offer_audits`: freshness is worked out on every read, so no machine action flags, re-runs or removes an audit. The team's audit settings are not an input. The audit section carries the answer as `data-audit-freshness` — `none` where there is no result to judge — beside `data-audit-state` and `data-audit-available`, standing in for neither. `tests/lib/audit/freshness.test.ts` is the reference.
- `src/pages/api/offer-refetch.ts` is the reference for a route that overwrites a row (FR-009): everything that can be checked for free, then one fetch, then one update judged by its error and by the number of rows it reached. The stored `source_url` is not trusted — any member can change it through the Data API — so it goes through `normalizeOfferUrl` before anything is fetched; the update carries the mapper's columns and `fetched_at`, never `id`, `source_url`, `created_by` or `created_at`; and whether the listing changed is told from the row read at the start and the row the update returned, both through `readAuditOffer`, never from the freshly mapped object. The route reads and writes `public.offers` alone: `refetchNoNotesConfig` in `@eslint.config.js` makes an import of the notes module an error there and in `src/lib/offer-refetch.ts`, and no audit is touched. `src/lib/offer-refetch.ts` is the reference for the lost-facts rule (`@context/foundation/prd.md`, Open Questions, resolved block): a fact the stored listing states and the fetched one no longer does stops the save until the member agrees to lose those columns, the agreement covers only the columns the member was shown, and a stated value that changed into another is saved without a question. `src/lib/otodom/failure.ts` holds the fetch-failure sentences the two ingestion routes share, each with the ending its route needs — a failed re-fetch never says that nothing was saved, only that the stored data stayed. `tests/pages/api/offer-refetch.test.ts` is the reference test.
- `supabase/migrations/20261011160031_offers_archive.sql` is the reference for a column a trigger signs on a table every member may write (FR-014). `offers_update_authenticated` lets any member write any column of any offer through the Data API, so a signature the client set could be forged: the client only states an intent — any non-null `archived_at` to archive, `null` to restore — and the triggers put the database's time and `auth.uid()` in its place, keep both columns as they are for as long as the offer stays archived, clear both on a restore and start every new offer live. No policy and no grant changes; the trigger is the single gate on the signature. `archived_by` is `on delete set null`, with its deleted-account branch before every other rule, and a `null` signature beside a date means a deleted account and nothing else — which is why an archiving without `auth.uid()` is refused.
- `src/lib/offer-archive.ts` is the reference for reading the archive and for what „ostatnio zarchiwizowane” means: `loadArchive` is the one read the section under the board and `/offers/archive` share — most recently archived first, the archivers named with one query through `resolveAuthors` — and a failed read is its own state, never an empty archive, which would say that nothing was hidden from the board. `RECENTLY_ARCHIVED_MS` and `isRecentlyArchived` hold the 7 days, with the clock passed in, while the link beside the section counts everything in the archive; `archiveOf` is the card's state, taken from the row and never from the address. `tests/lib/offer-archive.test.ts` is the reference test. `src/pages/dashboard.astro` lists live offers only, and a failed read of the archive changes nothing on the board.
- `src/pages/api/offer-archive.ts` is the reference for a route that moves a row between two states, where the first member to act wins: the write carries `archived_at` alone, never `archived_by`, and is filtered by the state it expects to leave, so of two members archiving the same offer the first stays signed and the second reaches no row — reported as a change in between, never as a success. An offer already in the state asked for is not written to and is not an error, and `intent` has no default, since the two actions undo each other. The route reads and writes `public.offers` alone: `archiveNoNotesConfig` in `@eslint.config.js` makes an import of the notes module an error there and in `src/lib/offer-archive.ts`, and no audit is touched. `tests/pages/api/offer-archive.test.ts` is the reference test. `src/components/offers/OfferView.astro` carries the row's state as `data-offer-archived="true"|"false"`, standing in for none of the audit's attributes beside it; `src/components/offers/RecentlyArchived.astro` on `/dashboard` and `src/components/offers/OfferArchive.astro` on `/offers/archive` carry the archive's read as `data-archive-state="ok"|"error"` and each archived offer as `data-archived-offer`, which `scripts/smoke.mjs` checks, because a failed read renders with 200 just like an empty archive.
- `src/pages/api/offer-delete.ts` is the reference for a route that deletes a row (FR-015): everything that can be checked for free, then one delete that asks for the deleted rows back and is judged by its error and by their number, with nothing read before it. Zero rows is a result of its own, neither a success nor a failure — the offer was already gone, logged as `already_gone` and told as `?deleted=gone`, never as `?deleted=1` — and the route's doc comment states the one state that reads the same and cannot be told apart. The entry of a deleted offer carries `otodom_id` from the deleted row, since afterwards there is no row to look it up in. `return` only chooses between two fixed addresses and is never put into one. Notes and the audit go with their offer through `on delete cascade` and through nothing else: the route reads and writes `public.offers` alone, and `deleteNoNotesConfig` in `@eslint.config.js` makes an import of the notes module an error there. `tests/pages/api/offer-delete.test.ts` is the reference test. `src/pages/api/notes.ts` is the reference for a second action on a route that saves: `intent=delete` beside the default `save`, a delete filtered by the offer and by the session's member — never by a note id or an author from the form — judged the same way, with `?note=gone` for zero rows, and a failure named `&form=note-delete` so the card does not open the note editor for it. `tests/pages/api/notes.test.ts` is the reference test. `src/components/offers/DeleteNotice.astro` and `src/components/offers/NoteDeleteNotice.astro` read those results through a whitelist; the second shows nothing while the member has a note, and a failed read of the notes counts as having one.
- `supabase/migrations/` — create files with `supabase migration new <short_description>`, never by hand. `supabase/migrations/20260922202756_create_offers.sql` is the reference for a new table: RLS enabled and one policy per operation for `authenticated` in the creating migration, none for `anon`, per the rules under `### Secrets and data access`. Migrations reach the hosted project with `npx supabase db push` before the Worker that needs them deploys (`@context/foundation/deployment-runbook.md`). A human or the agent may run it, but the agent never pushes without the user's consent: it runs `npx supabase db push --dry-run`, shows the list of migrations matched against `supabase/migrations/`, asks, and pushes only on a yes — every time, since consent to one push does not carry to the next. It stops without asking when the list holds anything unexpected. `supabase login` and `supabase link` are one-time, interactive steps and stay the user's (`npx supabase projects list` shows the project ref). `supabase db reset --linked` is never run, by anyone.
- `supabase/seed.sql` is the reference for local-only fixtures: it creates three confirmed `@vetpad.local` accounts so note attribution (FR-013) can be exercised against a local database. It is wired through `[db.seed]` in `supabase/config.toml` and runs on `supabase db reset` and on a fresh `supabase start`. Two rules it carries. Its credentials are published — the repository is public — so nothing that is a real address or a reused password goes in it. And seeds are **not** inherently local: `supabase db reset --linked` wipes the hosted database and runs this file against it; `supabase db push` does not run seeds. `scripts/smoke.mjs` signs in with `sigaretif1@vetpad.local` and `sigaretif2@vetpad.local` from this file, so removing or renaming either account breaks the smoke job. `scripts/account-deletion.sql` deletes `sigaretif3@vetpad.local` inside a transaction it rolls back, and refuses to run without that account and `sigaretif1@vetpad.local`, so removing or renaming the third account breaks the same job; `scripts/audit-state.sql` refuses to run without `sigaretif1@vetpad.local` and `sigaretif2@vetpad.local`.

## Commands

Scripts are in `@package.json`. Two commands CI runs that are **not** npm scripts: `npx astro sync` and `npx astro check` — run both locally before pushing, or the `ci` job fails on something `npm run lint` never sees. The `ci` job also runs `npm test`, after `npx astro check` and before `npm run build`, with no secrets.

## Conventions

- Import through the `@/*` alias, not deep relative paths.
- Default to `.astro`. Reach for a React island only when the component needs state, effects or DOM event handlers, and mount it with an explicit `client:*` directive — see `src/components/auth/SignInForm.tsx` mounted from `src/pages/auth/signin.astro` with `client:load`.
- React components are `PascalCase.tsx`. A form island default-exports (`src/components/auth/SignInForm.tsx`); a component it composes uses a named export from `src/components/form/` (`FormField.tsx`, `PasswordToggle.tsx`, `SubmitButton.tsx`, `ServerError.tsx`). A closed list is `src/components/form/SelectField.tsx`, whose hidden input carries the value a native POST submits. `src/lib/` modules are kebab-case.
- Merge Tailwind classes with `cn()` from `@/lib/utils`; never concatenate class strings.
- API routes that back an HTML form submit read `FormData` and report failure by redirecting with `?error=<encoded message>` — never JSON. `src/pages/api/auth/signin.ts` is the reference; `signout.ts` has no failure path — it redirects to `/` either way and skips the sign-out when Supabase is unconfigured, which is the zero-config rule above, not a gap to fill. A page with more than one form tells their errors apart with `&form=<name>` after `?error=`, since the page cannot read the `#` fragment; `src/pages/api/criteria.ts` is the reference. A form with more than one action carries it in a controlled hidden `intent` field, never only in the submit button's `name`/`value`: the island disables the button on submit, and Firefox leaves a disabled submitter out of the form data — `src/components/criteria/TeamLimitsForm.tsx` is the reference. An endpoint driven by `fetch` from a React island (progress, autosave, archive) may answer with JSON instead of a redirect, and `src/pages/api/audits.ts` is the reference — a second one follows it instead of inventing a second style. The request stays a form `POST`. A request without a session is redirected to `/auth/signin`, and that is the only redirect the route makes; every other answer, a refusal and a failure included, is `200` with a stream of JSON lines whose last line says how the action ended. `src/components/offers/AuditRunner.tsx` is the reference island, and its reading of the answer lives in `src/lib/audit/stream.ts` as pure functions: only a redirected answer is a sign-out, an answer that is not the stream — the 503 page of an Auth outage among them — is neither a sign-out nor a failed action, and a body that ends without its last line says nothing about how the action ended, so the island reloads the page and lets the server tell the state instead of offering a retry.
- Do not add `zod`, `valibot` or another validation library to `@package.json` without the user's explicit go-ahead. Validation is hand-rolled — `src/lib/otodom/url.ts` is the reference for URL normalisation (FR-005). The model's structured audit output was decided the same way in S-04: the provider enforces the answer's shape from `AUDIT_OUTPUT_SCHEMA`, and `readAuditOutput` and `readFindings` in `src/lib/audit/schema.ts` are the reference for reading a JSON value that is not trusted — the model's answer on arrival, a stored row on every read — while `tests/lib/audit/schema.test.ts` keeps the schema and its TypeScript type in step. The next case is raised as a decision too, never settled by installing a library.
- Every log entry goes through `logEvent` in `src/lib/log.ts`, the only module under `src/` that calls `console` — `no-console` is an error everywhere else (`@eslint.config.js`). `src/pages/api/offers.ts` is the reference for a route that logs every way out with one entry. An entry carries identifiers, codes and tokens from the reporter's whitelist — never Postgres' `details`, the fetched page's HTML, the `ad` payload, an email address or a query string, and from the audit never the prompt, the listing's text, an excerpt, a requirement or the model's answer; a field the list lacks is added to the list, never passed around it. A refusal the product expects is `info`, a failure is `error`. A call that is paid for or may take minutes gets an entry before it as well as one on every way out — `started` in `src/pages/api/audits.ts` is the reference. The model provider's error messages are held back from the log as well, because one can quote the request, and the request holds the listing. They stay in the provider's module, with one narrow exception, the user's decision of 2026-10-09: the field `provider_error_message` carries what the model provider said was wrong with a request it rejected — a `400 invalid_request_error` that is not a billing state, and no other failure — cut short, and dropped whole when it repeats a run of the message that carried the listing. `rejectionMessage` in `src/lib/audit/provider.ts` is the reference; every other provider failure is logged by its reason, status, type and request id, and a member never reads the provider's words.
- A rule in this file names a reference instance — never a count, never a paraphrase of a file that already states it. Write "`src/pages/api/auth/signin.ts` is the reference", not "all three auth routes". A count drifts silently; a named path fails loudly when it moves.
- The code reviewer sees none of this file, so its criteria drift from it unless they are kept in step: a change here that adds or changes a product invariant (`## Product invariants`), a hard rule (`## Hard rules`) or a security or testing rule (`### Secrets and data access`, `## Testing`) updates the criteria in `packages/code-reviewer/src/prompts/system.ts` in the same change — and, while the change `ci-cd-code-review` is still open, the section "Code Review Criteria" of `context/changes/ci-cd-code-review/requirements.md` first, since that file takes its text from there.

### UI

- A new view is built only from the tokens in `src/styles/global.css` — role classes such as `bg-card`, `text-muted-foreground`, `text-link` — and the components in `src/components/ui`. A colour literal in a view (`white/10`, `blue-100/80`, a hex) is a bug. The dark theme is the only one; `class="dark"` in `src/layouts/Layout.astro` switches it on.
- `npm run lint` enforces the previous rule: `tokensOnlyConfig` in `@eslint.config.js` fails a Tailwind palette utility (border sides, rings and ring offsets included), an arbitrary colour in brackets (hex, `rgb()`/`hsl()`/`oklch()`…, `color-mix()`), a colour in a `style` attribute, `bg-cosmic` or `backdrop-blur` anywhere under `src/`. Its `ignores` list is empty and nothing is ever added to it — a lint error there is fixed with a token, not with an exception.
- A new app view renders inside `src/layouts/AppLayout.astro` (frame, Topbar, a `notice` slot for page banners); `src/pages/offers/[id].astro` is the reference.
- A missing primitive comes from `npx shadcn add <name>`, followed in the same change by the ritual the CLI makes necessary here: import `cn` from `@/lib/utils`, delete `"use client"`, import `Slot` from `@radix-ui/react-slot` (`src/components/ui/button.tsx` is the reference), and drop the `cn` and `radix-ui` packages from `@package.json` if the CLI added them. For `label`, the ritual goes one step further: the CLI's `Label` wraps `@radix-ui/react-label` through the `radix-ui` package, and it is rewritten to a native `<label>` with the registry's classes instead (`src/components/ui/label.tsx` is the reference) — no `@radix-ui/react-label` in `@package.json`.
- A primitive whose behaviour lives in a Radix package other than `react-slot` (dialog, alert-dialog, popover, select, dropdown-menu…) keeps Radix — the user chose it on 2026-09-26 over native `<dialog>`/`<select>`, for the focus trapping, Escape handling and accessibility it brings, so the plan does not ask again. The ritual changes for it in one place: instead of dropping Radix, install the per-primitive package the component needs (`@radix-ui/react-dialog`, …) and import from it, the way `button.tsx` imports `Slot` from `@radix-ui/react-slot`; the umbrella `radix-ui` package the CLI adds is still dropped, and the plan names the new dependency. `src/components/ui/select.tsx` with `@radix-ui/react-select` is the reference, and `src/components/ui/alert-dialog.tsx` with `@radix-ui/react-alert-dialog` follows it; its overlay takes the `bg-overlay` token, since the registry writes that colour as a literal.
- An action that cannot be undone is confirmed in `src/components/form/ConfirmDialog.tsx` (FR-015): a button that opens the dialog, and in the dialog a native form `POST` whose hidden fields carry everything the route reads. The confirmation is a `SubmitButton`, never `AlertDialogAction` — that one closes the dialog on click, which unmounts the form from the portal before the browser has sent it — and the dialog cannot be closed while the form is on its way. A server render holds no dialog, so the page carries no delete form at all and nothing can be deleted with one click or with JavaScript off. `src/components/offers/DeleteOfferForm.tsx` is the reference island, and the next irreversible action uses the composite rather than `window.confirm`.
- A change to how the offer card looks goes through `/dev/offer-card` (`src/pages/dev/offer-card.astro`, fixtures in `src/pages/dev/_offer-fixtures.ts`): when the change is gated (see the last point below), screenshot every state there. A new card state gets a fixture there. The audit section goes through the same page: `OfferAudit` with its `AuditRunner` island renders there in every state of the audit's data and of a run, each on its own in a column as wide as the team column, and a new audit state gets an entry there. `AuditRunner`'s `preview` prop exists for that page alone — it opens the island in a state a run only passes through, and sends nothing. The archive goes through the same page: the card of an archived offer for each way its archiver reads, the audit section of an archived offer, `ArchiveNotice` and `DuplicateNotice` for an archived offer render there, and a new archive state of the card gets an entry there. The page renders under `astro dev` only and answers 404 everywhere else, which `scripts/smoke.mjs` checks on the production preview.
- A change to how `SignInForm`, `AddOfferForm`, `NoteEditor`, `TeamLimitsForm`, `RequirementsEditor`, `AuditSettingsForm`, `RefetchForm`, `ArchiveForm` or `DeleteOfferForm` looks goes through `/dev/forms` (`src/pages/dev/forms.astro`) the same way: it renders each of these forms in every named state, built from the same `src/components/form/` composites the forms use in production. A new form state gets a section there. A dialog is modal, so no section there opens one by itself: `?open=<name>` on that page names the one dialog to render open. Same dev-only/404 rule as the card kitchen sink, checked by the same `scripts/smoke.mjs`.
- A change to how the offer board looks goes through `/dev/board` (`src/pages/dev/board.astro`) the same way: every board state (list, empty, read error, sort controls, the audit statuses with a failed read of the audits and of their freshness, and the row states) renders there from `src/pages/dev/_offer-fixtures.ts` through the production components. The section under the board and the archive page go through it too: `RecentlyArchived`, `OfferArchive` and the row states of `OfferArchiveItem` render there in every state of the archive's read, a failed one among them. A new board or archive state gets a section there. Same dev-only/404 rule, checked by the same `scripts/smoke.mjs`.
- A change to how `/criteria` looks goes through `/dev/criteria` (`src/pages/dev/criteria.astro`, fixtures in `src/pages/dev/_criteria-fixtures.ts`) the same way: every state of the view renders there through `CriteriaView` — the audit settings' section and its failed read among them — and its forms' own states are on `/dev/forms`. A new criteria state gets a section there. Same dev-only/404 rule, checked by the same `scripts/smoke.mjs`.
- A change to how the error pages `/500` and `/503` look goes through `/dev/errors` (`src/pages/dev/errors.astro`) the same way: both views render there through `src/components/ErrorPage.astro`, the component the production pages render. A new error view gets a section there. Same dev-only/404 rule, checked by the same `scripts/smoke.mjs`.
- Whether a change that alters a view runs the visual gate is the user's call, not a default: `/10x-plan` asks and records the answer in the plan. A gated change carries in its plan the 7-state matrix (default, hover, focus, disabled, error, empty, loading) with every absent state named „nie dotyczy” and its reason, screenshots every state with `scripts/ui-screenshots.mjs` into its change folder, and re-runs the gate after `/10x-impl-review` triage changed the view, before the commit. A gated new view with more than one state gets its own `/dev/<view>` page on the pattern of `/dev/offer-card` (dev-only, 404 elsewhere, a step in `scripts/smoke.mjs`) and a set in `scripts/ui-screenshots.mjs`. An ungated change still passes `npm run lint` and keeps the existing kitchen sinks rendering — a new card or form state gets its fixture or section either way.

## Testing

`npm test` (Vitest, configured in `vitest.config.ts`) runs the unit and render tests under `tests/`, with no network and no secrets; `scripts/smoke.mjs`, `scripts/account-deletion.sql` and `scripts/audit-state.sql` are the test surfaces that need a live local Supabase — what they cover and what they need to run: `@README.md`.

- Any change to the surface of `src/pages/api/` — adding a route, removing one, or changing an existing route's contract — must be reflected in `scripts/smoke.mjs`, and in the `smoke` job of `@.github/workflows/ci.yml` if the flow needs different setup.
- `scripts/smoke.mjs` signs in with an account from `supabase/seed.sql` and checks that registration is closed, both in the app's routes and in Supabase Auth (FR-001). A change that re-enables registration, or removes that account from the seed, turns the smoke job red.
- Before it signs in, `scripts/smoke.mjs` sends a forged session cookie on a protected page and on a form route and expects the sign-in redirect, because a session Auth refuses is a sign-out and never the 503 page. `requestWithForgedSession` in that file is the reference for a step that sends a cookie instead of the cookie jar and stores nothing from the answer. Smoke runs against a live Auth and cannot play an outage; `tests/middleware.test.ts` covers that side.
- `scripts/smoke.mjs` also creates two fixture offers as the first seeded account, straight through the Data API, puts a note of each seeded account (the second is `sigaretif2@vetpad.local`) on both, and judges every write that could reach another member's row in `public.offer_notes`, `public.offers` and `public.member_requirements` by whole rows: `withSnapshot` in that file is the reference for comparing another member's rows before and after a step, and its control steps fail the run when the comparison stops seeing a change. It deletes both offers again as its last notes steps — which is why it never runs against production. It also changes the team's shared limits and saves requirements for both seeded accounts; its cleanup writes back the limits it read at the start and deletes both accounts' requirements, so requirements typed by hand for those accounts in the local database do not survive a run. The team's audit settings are changed and written back the same way. With one fixture offer stating a price and no area and the other an area and no price, it also checks on `/dashboard` that the offer missing the sorted value stands below the one that states it, in both directions — `fixtureBoardOrder` in that file is the reference for proving a rule that lives in the SQL query, which a unit test cannot.
- For the audit, `scripts/smoke.mjs` works straight against Supabase and reads the pages, and never runs an audit. It judges `public.audit_settings` and `public.offer_audits` by whole rows, as it does notes, starts an attempt on the second fixture offer through the Data API, and leaves the first fixture offer without one for the whole run: that offer's card must carry `data-audit-state="none"` whatever `data-audit-available` says beside it, and the second offer's card is the control that keeps a card answering `none` for every offer from passing. It also expects `data-audits-state="ok"` on `/dashboard` and `data-audit-settings-state="ok"` on `/criteria`. A step that needs an audited offer, or one whose attempt has a state, writes the row through the Data API the same way — never through the route.
- For audit freshness, `scripts/smoke.mjs` completes that attempt through the Data API once its control step has failed it — a takeover, then a result holding the criteria revision as it stands and a listing fingerprint the script computes itself. `fixtureListingFingerprint` in that file is a second implementation of the `v1` format, kept apart from `src/lib/audit/input.ts` on purpose: the card's `data-audit-freshness="fresh"` is the proof that the two agree, and a change of the format without a new version turns it red. It then changes that offer's title, with every note on both fixture offers the same row afterwards, and expects `stale` on the card and `data-audit-status="stale"` on that offer's board row under `data-audit-freshness-state="ok"` — after a control step that read `audited` on the same row. The first fixture offer carries `data-audit-freshness="none"` throughout. These steps stand after every step that changes the criteria and before cleanup, which moves the revision again; a step added between them that touches the criteria or the second fixture offer's listing breaks `fresh`.
- To `POST /api/offer-refetch`, `scripts/smoke.mjs` sends only requests the route ends before it fetches anything — no session, a forged session, an id that is not a uuid, an offer that does not exist. `requestRefetchOfMissingOffer` in that file refuses a fixture offer's id outright and is the reference for a smoke step on a route that would go on to otodom.pl. What a re-fetch does to a row is covered against a stubbed portal in `tests/pages/api/offer-refetch.test.ts`, where every scenario states how many requests reached otodom and how many writes reached `public.offers`.
- For the archive, `scripts/smoke.mjs` archives the first fixture offer through `POST /api/offer-archive` and restores it the same way, with every note on both fixture offers the same row after each, and judges the signature by the offer's whole row: the second seeded account's PATCH of `archived_by` or of `archived_at` on the archived offer answers with the row and leaves it as it was, and that account's archiving of the live offer under a forged date and signature is the control step — reported as changed, and stored with the caller's id and the database's time. `fixtureOnDashboard` in that file is the reference for reading where an offer stands on a page that links it from more than one place: the board is the page up to the „Ostatnio zarchiwizowane” section, which links an archived offer's title to the same address a board row does, and its control step reads the live offer before anything is archived. ## Git workflow

Changes are written in the `master` working tree, may be committed there phase by phase by `/10x-implement`, and leave it through one of two skills, and the agent asks which one rather than assuming (see `### Git` above). Each skill's own description is the account of what it does; the parts worth knowing before you start are these. `/git-ship` moves the change — local commits and uncommitted work alike — onto a branch, so afterwards it is no longer in your tree: it points local `master` back at `origin/master` once the branch is pushed. That is a ref move, not a rewrite — the commits keep their SHAs on the branch, so the SHAs `/10x-implement` wrote into `## Progress` stay valid. `/git-land` leaves it where it is and pushes `master` itself, so afterwards your tree is clean but the change is on the default branch with nothing between it and `origin` — it confirms once before that push, listing the local commits it is about to publish. Both stop when `master` is behind `origin`, and `/git-sync` (fast-forward only) is what unblocks them — unless `master` also carries local commits, in which case the two have diverged, `/git-sync` refuses too, and the call is the user's.

- Branch slugs are 2–5 words; `/git-ship` normalises the rest. `/git-land` asks for no slug — it creates no branch. When the change folder is known, its `<change-id>` is the natural slug.
- Commit subjects: English, imperative, one line, 70 characters max, no `feat:`/`fix:` prefixes, no trailing period. The one exception is `/10x-implement`: its commits use the skill's own Conventional-Commits form, `<type>(<change-id>): <phase title> (p<N>)`, and that format wins for the commits it authors.
- Do not overstate automation. Because every fetch, re-fetch and audit is a deliberate manual action (see Product invariants), a message calling one of them "automatic" misdescribes the product. If the behaviour stops to ask the user, write "offer", "prompt" or "ask".
- PRs target `master`; both CI jobs must pass (`@.github/workflows/ci.yml`). A `/git-land` push skips that gate entirely — CI runs on `master` after the fact, so anything that would not survive review belongs in a PR.
